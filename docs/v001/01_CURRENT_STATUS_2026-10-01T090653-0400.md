# XtraType v.001 — Current Status Landmark

**Timestamp:** October 1, 2026 at 09:06:53 EDT (UTC-04:00)  
**Canonical project version:** **v.001**  
**Code baseline:** exact predecessor working tree whose inherited manifests identify `2.5.0`  
**Application-code delta in v.001 instantiation:** **zero bytes**

This document is the perpetual reset landmark for the beginning of the v.001 forward lineage. If later status becomes confusing, start here, verify the sealed baseline, and then walk forward through subsequent version documents.

## 1. Product state in one paragraph

XtraType is a Chrome Manifest V3 contextual annotation system with a native side panel, page/YouTube projections, local IndexedDB durability, optional PHP/JSON synchronization, typed anchors (URL, Time, YouTube, GPS, plus bounded custom schemas), image attachments, rendered-page snapshotting/history/comparison, live tab/navigation refresh, keyboard and omnibox entry, seven-day “young” annotation signaling, and a bounded invitation/account/messaging layer. PortaShape is the selected wraparound host/plugin/service architecture that will grow around XtraType while preserving XtraType as the contextual application; its host, package, grant, operation, plugin, Script Studio, Stay D.R.Y., Universal Publisher/Bridges, connector, and broader cross-client/runtime layers remain primarily specified rather than implemented.

## 3. Current extension topology — IMPLEMENTED

- `ext/manifest.json`: MV3, Chrome minimum 116, `activeTab`, `scripting`, `storage`, `sidePanel`, `contextMenus`, `tabs`, `webNavigation`, `geolocation`, `<all_urls>`, YouTube content script, `xt` omnibox keyword, `_execute_action` shortcut suggested as `Ctrl+Q` (`MacCtrl+Q` on macOS).
- `ext/service-worker.js`: privileged orchestration for context capture, side-panel/quick-bar opening, omnibox handoff, navigation broadcasts, badge updates, quick create/reply, page and YouTube projection queries, and screenshot/capture coordination.
- `ext/sidepanel/*`: primary author/composer and Annotations sections (the only reorderable pair), capture, timeline/compare, schema management, settings, account/messaging UI, and current-context status.
- `ext/content/page-ui.js`: on-demand page-owned quick-comment surface.
- `ext/content/youtube.js`: YouTube markers/toasts/replies with bounded navigation/player lifecycle.
- `ext/core/*`: anchors, bounded schemas, IndexedDB, record construction/validation, HTTP/sync/account API adapter, capture orchestration.

## 4. Current interaction behavior — IMPLEMENTED

- Open/toggle XtraType through the extension action; `Ctrl+Q` is bound to the action command.
- Sidebar context refreshes on active-tab change, normal URL navigation, SPA history-state navigation, and fragment changes.
- Omnibox: type `xt`, Space, optional text, Enter. XtraType opens the side panel, refreshes active context/selection, transfers omnibox text into the comment textarea, and focuses the composer.
- Highlighted page text is captured into the highlighted-text field when context acquisition succeeds.
- Attach-to built-ins are URL, Time, YouTube video, and GPS; custom inert target schemas can add bounded primitive target forms.
- URL UI includes Base URL plus collapsible Query & fragment handling.
- Time anchor supports one canonical UTC instant or a required start/end range.
- Annotations younger than or equal to the seven-day window are visually marked with a green tree and contribute to the page badge, including the user's own posts. Merely reading them does not clear youth/newness. `Mark all as old` explicitly resets the applicable current set; age also expires naturally.
- Snapshot button is in the panel header immediately before the quick-comment-bar button. It defaults to full-page capture; Capture settings can make it visible-viewport capture.
- The author and Annotations sections can be reordered and persist their order; other modules are not reorderable.

## 5. Local persistence — IMPLEMENTED

IndexedDB remains:

- database: `portashape-xtratype`
- version: `1`
- stores: `annotations`, `blobs`, `schemas`, `snapshots`, `events`

Compatibility anchors remain:

- `Context.Annotation` schemaVersion `2`
- `Revision.Snapshot` schemaVersion `1`

A local annotation commit precedes optional server success. Dirty/error local records are protected from blind remote overwrite. There is no current distributed tombstone/conflict protocol.

## 6. Anchor system — IMPLEMENTED

- **URL:** bare HTTP(S) base identity with query mode `ignore | selected | all`, included query pairs, and fragment mode `ignore | include`.
- **GPS:** latitude/longitude with optional positive radius; deterministic quantized key; radius applicability.
- **YouTube:** validated video ID/URL with optional start and end seconds; whole-video null time remains distinct from zero.
- **Time:** canonical millisecond UTC instant (`timestamp`) or canonical start/end range with end strictly after start.
- **Custom:** installed bounded object-like schemas with primitive properties; not arbitrary executable schemas and not a plugin system.

## 7. Capture/history — IMPLEMENTED with known boundaries

Visible and full-page capture use pinned tab/window/document/URL/page metrics, paced visible-tab screenshots, extraction, tile assembly, cleanup, and local snapshot/blob persistence. Current limits include 40 million pixels, 28,000 pixels per dimension, and 30 tiles. Dynamic documents can fail identity/geometry checks. Fixed/sticky content can repeat. Snapshot server behavior is upload-oriented; remote snapshot binary hydration is not a complete restore system. Pixel comparison is a visual RGB comparison aid, not semantic diffing.

## 8. PHP/JSON service — IMPLEMENTED, local-default

The PHP layer uses `JsonRepository` with locked read/mutate behavior and temp-write/rename replacement. Raw data lives outside the served app paths under `var/`. API bootstrap enforces configured Host/Origin boundaries, request sizes/content types, an `X-XtraType-Client` header for mutating calls, and bearer authorization after account initialization where routes require it.

Current API families: health, annotations, schemas, snapshots, events, auth, invites, admin, contacts, messages, and group chats. Media uses validated content-addressed storage/retrieval.

This is not public-hosting certification. TLS termination, hardened production deployment, E2E messaging encryption, distributed conflict resolution, remote revocation of already-local data, generalized cross-device sync, and complete binary restore are not established by this baseline.

## 9. Accounts, invitations, contacts, DMs, group chats — IMPLEMENTED bounded layer

- First successful registration becomes seed admin without an invitation.
- Later registration requires an unused single-use invitation whose creator remains enabled.
- Passwords are stored via PHP `password_hash`; plaintext passwords are not profile payloads.
- Bearer session tokens are returned to clients; server session records store SHA-256 token hashes.
- Sessions default to the bounded lifetime defined in `Auth.php` (30 days in this baseline).
- Enabled users can normally create at most one invitation per **fixed EST (UTC-05:00, year-round) calendar day**, resetting at fixed-EST midnight.
- Admin can globally disable central system use, globally disable invitation creation, disable individual accounts, and remove individual invite-creation permission.
- Per-user profile JSON documents live below `var/profiles/<user>/` for profile/registration/invitation/contact-group/group-chat membership payloads.
- Contact groups are user-owned grouping metadata.
- Direct messages are authenticated central JSON records.
- XT Group Chats use case-sensitive five-character base62 codes and `https://xtratype.com/gc/#####` canonical URLs. Membership is required to read/write; creator controls grants in the current implementation. Authorized group-chat URLs render the chat in the side panel's normal annotation-feed region.

### Invitation scale policy

A separate owner-held **confidential total invitation ceiling** governs the current testing phase. Its number is intentionally absent from the repository. The code-level one-per-day rule is not a substitute for that total operational cap.

## 10. Web surface — IMPLEMENTED narrow companion

The responsive PHP web client provides server-first annotation/context/schema functionality and simple account registration/login. It has no extension privileges and no IndexedDB-equivalent offline authority. Shared anchor/schema browser core is kept byte-aligned with extension copies by the repository sync/parity process.

## 11. PortaShape — SPECIFIED target, not broadly implemented

The sealed companion specifies the host/package lifecycle, installations, grants, invocation/receipt/event protocol, plugin repository namespaces, client bridge, richer XtraType sidecars/AnchorBundle/relationships, Script Studio, Stay D.R.Y., Universal Publisher/Bridges, external connector standards, additional clients, and staged acceptance. The companion registry contains the established module/component/contract/operation/permission/interactions/surface/stage/acceptance inventories. Those target definitions remain authoritative design input but must never be used as proof of executable completion.

The current 2.5-era bounded account/messaging layer is an owner-directed implementation that post-dates the companion's original service deferral. It does not silently instantiate the broader PortaShape identity/sync/backend service plane.

## 13. Known architectural boundaries to protect

- Preserve current database/record identities unless a migration is explicitly designed.
- Keep local commit truth separate from remote replication truth.
- Do not equate page-owned overlays with secrecy boundaries.
- Do not equate custom schema data with executable plugin code.
- Do not transfer package grants, credentials, or privileged execution authority through imported data.
- Do not turn unknown external-effect outcomes into success/failure by guess or blind retry.
- Do not call the local JSON service a fully hardened public platform backend merely because accounts now exist.
- Do not collapse XtraType into PortaShape; XtraType remains the contextual application and first-party client, while PortaShape is the wraparound host/platform architecture.

## 14. What “healthy growth” looks like from here

A healthy future remains recognizably additive: more robust XtraType contextual relationships, more trustworthy sync/identity where deliberately designed, PortaShape host and plugin boundaries implemented behind explicit capability grants, community scripts/modules/plugins that cannot silently inherit privileged authority, richer publishing/connectors with truthful effect receipts, and new clients that reuse portable contracts without pretending to possess unavailable host capabilities.
